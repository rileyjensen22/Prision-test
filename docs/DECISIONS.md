# Decisions

## Phase 0

- **Seed writes JSON, not Postgres (yet).** The data model arrives in Phase 1; `make seed` produces `var/seed.json` from `/config` plus synthetic people. Rejected: stubbing tables early (would be thrown away).
- **Config is YAML in `/config`, validated by `isd.config_loader`.** Phase 1 moves it into versioned DB tables (invariant 9); YAML stays as the seed source.
- **Python `>=3.12`.** Dev sandbox has 3.13; CI and Docker use 3.12.
- **Makefile uses a local `.venv`** so `make test` needs no Docker/Postgres in Phase 0.
- **Playwright `CHROMIUM_PATH` env override** for sandboxes with a preinstalled browser; CI downloads its own.
- **Stub scripts** for `simulate-week` and `export-public-log` exist so every Makefile target runs; real logic lands in Phases 7-8.
- **Tailwind v3** chosen over v4 for stable PostCSS config.

## Phase 1

- **Two DB roles.** `isd` owns the schema (migrations/seed only); `isd_app` is the runtime role. Migration 0001 revokes UPDATE/DELETE/TRUNCATE on `audit_log` and `config_versions` from `isd_app`. Rejected: single role (grants alone would not hold against the app's own credentials).
- **Trigger as second layer.** `forbid_mutation()` BEFORE UPDATE/DELETE/TRUNCATE triggers fire for every role, including the owner. Known limit: a Postgres superuser can disable triggers or set `session_replication_role=replica`; the hash chain is the detection control for that case (`GET /audit/verify`).
- **Hash chain computed in the app, under `pg_advisory_xact_lock`.** Gapless `seq` (not a DB sequence, which can skip) so deletions show as gaps. Each hash covers `prev_hash` + canonical JSON of all fields. Payloads must avoid floats. Rejected: DB-side hashing (needs pgcrypto, harder to test/version).
- **Corrections, not edits.** `POST /audit/corrections` (admin) appends an entry with `ref_seq` to the original. Admins have no other write path to the log.
- **`config_versions` is append-only too** (invariant 9 history). Current config = highest version per section; each change writes an audit entry and requires a reason.
- **Auth:** argon2 passwords, HMAC-signed expiring bearer tokens (stdlib, no JWT dependency). Role is re-read from the DB on every request so deactivation/role changes apply immediately. Mock SSO interface still to do. Login rate limiting is Phase 8.
- **RBAC check by test:** `test_every_non_public_route_has_a_role_guard` fails if any new route lacks `require_roles`.
- **Audit read access:** `admin` and `auditor` only for now; revisit when the staff dashboard (Phase 5) needs supervisor views.
- **Tests need Postgres** (`make db-local`, or the CI service). They create a throwaway `isd_test` DB via Alembic. Tamper tests disable the trigger inside a transaction that is rolled back.
- **Data model scope:** tables for staff, config, residents, cells/devices/assignments, contacts, point events, sanctions (with `issued_by <> confirmed_by` CHECK), appeals, offense flags, audit log. Engine behaviour is Phase 2.

## Phase 2

- **Pure engine, thin services.** `api/isd/engine/` is I/O-free (config, ceiling, tiers, entitlements, authority) so Hypothesis can hammer it. `services/` loads facts, persists decisions, and writes audit entries. A test fails if anything outside `entitlement_service` calls `compute_entitlements` (invariant 2).
- **`get_entitlements(session, resident_id, at_time)` is read-only** (tested), so Phase 6 sandbox/time-travel is safe. It never writes tier changes; `points.evaluate_tier` does, and runs after each point event. A daily job (Phase 8 `simulate-week`) must also call it so a deferred weekly drop eventually happens.
- **Earned tier vs effective tier.** Earned tier follows points (with hysteresis). Effective tier = `min(earned, repeat-return ceiling)`. The ceiling never lowers points or earned tier. Reasons distinguish `TIER_LOCKED` (not yet earned) from `TIER_CEILING` (earned but capped).
- **Tier history table** (`tier_history`) instead of a mutable `earned_tier` column: the current tier and the last drop time are derived, so the 7-day drop rule is checkable from data. Promotion may jump several tiers; a drop is always exactly one level, and drops are at least 7 days apart (boundary inclusive).
- **Sanction vs points are separate.** A sanction only locks features. When a sanction becomes active (immediately, or on confirmation) a `confirmed_{minor|major}_infraction` point event is recorded. Overturning on appeal records an `infraction_reversal` event. Assumption: severity per infraction code is in `config/sanctions.yaml` (`DISRUPT`, `CELL_MESS`, `STAFF_DISRESPECT` = minor; `CAM_BLOCK`, `DEVICE_TAMPER`, `DEVICE_DAMAGE` = major). The spec didn't assign severities, so this needs customer sign-off.
- **Authority rules.** Needs a supervisor if the rule isn't `officer_immediate` or lasts over 24h. Evidence is required at issue time: a system event, or a report from a second staff member (not the issuer). `DEVICE_TAMPER` accepts only a system event. Once an officer hits the weekly cap (default 3 immediate sanctions in a rolling 7 days) further sanctions become `pending` for supervisor confirmation, rather than being refused. Only supervisors confirm, reject, or review appeals; the DB also has a CHECK that issuer ≠ confirmer. System-detected events may issue (never confirm). Rejected: letting admins confirm (spec says supervisor).
- **Lock starts at confirmation**, not at issue, for pending sanctions; end time = start + duration.
- **Appeals** can only be filed against active sanctions, one open at a time, and are due in `appeal_review_hours`. `overdue_appeals()` is available for the dashboard.
- **Config validation** now rejects unknown sanction scopes and any offense restriction that names a baseline feature.
- **Feature catalog** (`engine/features.py`) is the only definition of the protected baseline. Steps 3–5 of the composition only operate on non-baseline features, and property tests assert the baseline is never removed.
- **Contact-level blocks** are returned as `blocked_contact_ids` (they're per-contact, not per-feature) and apply at every tier.
- **Not yet done (later phases):** clean-day awards (needs the daily job), `valid_until` for the offline snapshot (Phase 3; `next_change_at` is the building block), HTTP routes for sanctions/appeals (Phase 5).

## Phase 3

- **Device identity by token.** Kiosk routes (`/device/*`) are authenticated by a per-device secret (hash stored in `devices.token_hash`), then resolved device -> open assignment -> resident. Rejected: unauthenticated device code (anyone on the network could read a resident's screen). The RBAC route-guard test accepts either a staff role guard or the device guard.
- **One payload, one code path.** `build_resident_view()` produces the `ResidentView` the kiosk renders. Phase 6 sandbox/mirror will call the same function (a test confirms `simulation` is the only field that differs).
- **Offline = fail closed.** `valid_until` = min(next sanction boundary, now + TTL). Past it with no connection, non-baseline features are paused client-side (`OFFLINE_STALE`). Rejected: trusting the cache indefinitely (a lock that should have started or ended would be wrong), or locking everything including baseline (violates invariant 1).
- **Server-time offset.** Staleness uses `Date.now() + (server generated_at - device time at fetch)`. This came out of the e2e offline test: a skewed device clock would otherwise extend or cut short the cache.
- **Appeals and Request staff are idempotent for offline replay.** Staff requests carry a `client_id` (unique); a duplicate appeal returns 409, which the queue treats as delivered.
- **Tier-locked vs restricted.** "Not unlocked yet" appears on the service tile only; the Restrictions list shows sanctions, offense restrictions, and the ceiling. Offense restrictions show the config `reason_text` (English only for now; localizing it needs a per-language field in the offense config).
- **Allowances show `used: 0`** until calls and commissary track usage in Phase 4.
- **Reading level** is stored and sent but not yet used to switch wording; captions flag is stored for video (stub). Both are staff-set only.
- **Staff-controlled settings and assignments** have API routes now (`PUT /staff/residents/{id}/settings`, `POST /staff/device-assignments`); both are audit-logged with a required reason. The staff UI for them is Phase 5.
- **E2E runs the real stack.** Playwright seeds a fresh `isd_e2e` database, serves the API with uvicorn on :8001 and the production web build on :4173, so the CSP and API contract are both exercised.
- **Known gap:** no login/rate limiting on device routes yet (Phase 8), and the device token lives in localStorage.

## Phase 4

- **Content and policy are versioned config.** Two new sections, `courses` (lessons, quiz, answers; bilingual) and `commissary` (catalog, prices in cents, per-item `min_tier` and blocked offense categories, `max_deposit_cents`). Edits are audit-logged like any config. Rejected: separate content tables (would duplicate versioning). Quiz answers are readable by staff roles via the config API but never sent to the device (tested). `load_engine_config` now loads only the sections the engine needs, and `seed_database` adds any missing section, so older databases keep working.
- **Education.** One sample basic course (`MONEY101`, +50) as specified, plus a tiny advanced course (`WORKMATH`) so gating can be shown; delete it if you want strictly one. Basic courses are gated by the baseline `basic_education` feature (never locks); advanced and program courses by `advanced_education`. Completion awards points once (unique per resident and course), through the normal point-event path so promotion and the weekly-drop rules apply. The demo loop needs a resident near a threshold: with the seed values one course (+50) cannot promote from 0 points, so the demo resident starts at 60. Quiz grading is server-side, so education needs a connection in v1 (offline lessons are a later option).
- **Attorney privilege enforced in layers (invariant 6).** (1) `TelephonyService` is the only path to a provider; for privileged calls it tells the provider not to record, never asks for monitoring data, hangs up and raises if a provider captured anyway, and refuses `recording()`. (2) The DB has CHECK constraints: a privileged call can't be `monitored` and can't have a `monitor_ref`. (3) `call_records` has no content columns (tested). (4) Staff access to call content (`fetch_recording`) is audit-logged, limited to supervisor/admin, and for attorney calls only logs a `monitoring_denied` entry with the call id. What is kept for attorney calls: that a call happened, the contact record, start/end, duration. Providers only receive an opaque phone reference.
- **Attorney contacts ignore no-contact blocks and the tier allowance.** Steps 3-5 never remove baseline, so an attorney call can't be blocked or metered. Which contacts count as attorney comes from `compliance.privileged_contact_types`.
- **Call limits.** Daily allowance = tier minutes; usage is the sum of today's non-attorney call seconds, shown in whole minutes rounded up. Each call is capped at the minutes left; the server clamps duration, and an abandoned call is closed at its cap. One call at a time per resident. Days and weeks are UTC for now (a facility time zone is a config item for later).
- **Monitoring notice.** Regular calls display "may be monitored and recorded" before and during the call; attorney calls display that they are private. Wording needs counsel review.
- **Commissary money is integer cents** in an append-only `trust_ledger` (UPDATE/DELETE/TRUNCATE blocked by trigger and revoked grants; DB CHECK for no overdraft). Entries are written under a per-resident advisory lock, each carrying `balance_after`; `verify_ledgers()` re-checks every balance and that each order matches its ledger entry (used by `simulate-week` in Phase 8). Orders are idempotent per `client_id`.
- **Order rules.** Commissary must be allowed by the entitlement engine; each item checks `min_tier` against the resident's effective tier and blocked offense categories; the order must fit the balance and the weekly dollar limit (`dollars_per_week`, ISO week in UTC). Entitlements now also return the resident's offense categories for this. Refunds exist as a ledger type but have no workflow yet.
- **Deposits** go through `PaymentProvider` (mock, deterministic ids). `POST /mock/deposits` (supervisor or admin) stands in for a family-payment webhook; it is idempotent on `idempotency_key`, bounded by `max_deposit_cents`, and audit-logged.
- **Telephony and payments are mocks behind interfaces** (`isd/interfaces`, `isd/mocks`), chosen in `isd/providers.py`. No network calls anywhere.
- **Not yet done:** texting/video/chess/reading/jobs stubs (Phase 7), staff views of calls and ledgers (Phases 5-7), clean-day points (daily job).

## Phase 5

- **Staff app = React pages over thin API routes.** `routers/staff_ops.py` and `services/staff_views.py` hold read models (roster, queues, outliers, feed, summary); every rule still lives in the engine and the Phase 2 services. The UI shows `can_confirm` / `can_review` computed by the server, but the server re-checks on every action (tested: a supervisor cannot confirm or review their own item, and an officer gets 403 on supervisor routes).
- **Role visibility.** Officers: dashboard, roster, resident detail (record infractions, change settings), config (read). Supervisors: plus confirmations, appeals, outliers. Admins: plus audit log and config editing. Auditors: read-only view of everything including the audit log, no write routes. Peer comparisons (outliers) are hidden from officers; the page is blocked in the UI and the API returns 403.
- **Evidence input.** A second-staff report names a real, active staff member who is not the issuer (the API now rejects unknown ids; found by an e2e test). System-event evidence takes a reference string. Both are shown to the confirming supervisor.
- **Outlier view.** Peers are same-role staff; each person is compared against everyone else in the group (leave-one-out) so one extreme person cannot hide by inflating the spread. Four measures: infractions recorded, sanctions applied, overturned-on-appeal rate, supervisor-rejection rate. Only high values are flagged; rates need at least `min_count` cases; the group needs `min_peers` others; thresholds live in `config/sanctions.yaml` (`outlier`: 30-day window, z >= 2). A flag is a prompt to look, not a finding. Limitation: there is no staff-to-resident assignment yet, so counts are not normalised by workload. Rejected: raw rankings (they would always flag someone).
- **Config editor** is a JSON editor with server-side validation and a required reason, plus a live preview of the repeat-return curve computed by the engine (`GET /staff/ceiling-preview`), so the formula is not duplicated in the UI. Only admins can save; every save is a new version and an audit entry. Rejected: a form per section (too much UI for v1; validation is server-side either way).
- **Audit page** (admin, auditor): verify the hash chain, and admins can append a correction that points at an entry. Nothing can edit or delete.
- **Staff sessions** use a bearer token in `sessionStorage` (cleared when the tab closes); a 401 signs the user out. Real SSO and idle timeouts are Phase 8.
- **Staff strings are English only** for now (the resident surface is bilingual, as the spec's resident requirements demand). The strings are inline, not in the i18n files; moving them is mechanical when a Spanish-speaking staff need is confirmed.
- **Resident activity timeline and monitored call metadata** (CLAUDE.md section 9) are deferred to Phase 7 along with the monitoring-access audit trail. Resident detail currently shows sanctions, points, and tier history.
- **Dev logins** (`make seed`): `officer1`..`officer3`, `supervisor1`, `supervisor2`, `admin1`, `auditor1`, all with the synthetic password `dev-password-not-secret`.

## Phase 6

- **Sandbox = same code path, different inputs.** `build_resident_view` and `get_entitlements` take optional `SandboxOverrides` (tier, prior returns, offense categories, hypothetical sanctions, ignore-real-sanctions, language/text size, and a time-travel `at_time`). Overrides change what goes *into* the engine, never its rules, so a simulated screen is produced by exactly the code that produces a real one. A test confirms that with no overrides the sandbox view equals the real view (apart from the `simulation` flag), and a property test confirms no override can remove the protected baseline.
- **"Zero writes" is enforced by the database.** The sandbox route uses a session that runs `SET TRANSACTION READ ONLY` and always rolls back, so Postgres itself refuses any write (tested directly: an insert inside the sandbox transaction fails). A second test fingerprints every table before and after a batch of sandbox requests (including invalid ones and time travel) and requires them to be identical, audit log included. Sandbox use is therefore not audit-logged (there is nothing to write to); it only exposes data staff can already see in the roster and resident page. Rejected: relying on code review for "no side effects".
- **Hypothetical sanctions** use negative ids so they can never be confused with real ones, and appeal buttons inside a simulation return a success state without calling anything (the staff page says so).
- **Time travel** is limited to 3 years back and 1 year ahead. Past views use tier history and the resident's real sanctions; a sanction that was later overturned is not shown as it would have been (known limit).
- **Live mirror is a logged session, not a video feed.** Supervisors and admins start a session with a written reason; starting and ending are audit entries (who, which resident, device, reason, length, frames). Sessions end at `mirror_max_minutes` (15) or after `mirror_idle_seconds` (60) without polling, and the expiry is logged. Auditors can read the history but not start sessions; supervisors see their own, admins and auditors see all.
- **What a mirror shows.** The kiosk reports its current route (`POST /device/screen`, route only, no content). The mirror redraws that route from the resident's current `ResidentView`, read-only. Screens whose content is live data (calls, shop, classes) show a labelled stand-in, not the contents. Fidelity is therefore "where the resident is and what the resident sees on the home, lock, appeal and tier screens", not a pixel copy.
- **Redaction is server-side and fails safe (invariant 6).** A mirror never shows: any screen while a privileged (attorney) call is active; the law library, grievance, medical and mental-health screens. The device does not even store those paths (it stores `/resident/redacted`), and the frame API returns no view and no path when redacting. Tested at the engine, service, and browser level, including that an attorney call starts and stops redaction live.
- **Nested routers:** React Router forbids a router inside a router, so the simulated resident app runs in its own React root. A unit test covers rendering it inside the staff app.
- **Fix found along the way:** `capped_by_ceiling` was false for a resident whose earned tier is 10 but whose ceiling is lower (no "next tier"), so the kiosk would have said "You are at the highest tier". It is now true whenever the earned tier has reached a ceiling below 10.

## Phase 7

- **Public log (CLAUDE.md section 10).** Off by default: `compliance.public_log_enabled` is false, so the export code raises and the script exits 2 without writing anything. Turning it on is a normal audited config change by an admin. The export writes static files only (`records.json`, `records.csv`, `summary.json`, `index.html`, `README.txt`, `manifest.json` with SHA-256s) and records the export itself in the audit log (counts and a manifest hash, nothing else). There is no live public API. Rejected: a public HTTP route (too easy to expose by accident).
- **Why the export cannot leak names.** Every record is built from an allow-list of eleven fields (`RECORD_FIELDS`) and re-checked by `assert_clean` before it is written; free text, evidence, notes, staff identities, cells and devices are never read into it. Residents and events appear only as salted HMAC pseudonyms (`PUBLIC_LOG_SALT`, not in the repo; stable across exports so trends are visible, changing the salt breaks linkage). Dates are coarsened to the Monday of the week. Counts under `public_log_min_cell` (3) are shown as `<3` in the aggregates. The test builds a story full of identifying strings (resident and staff names, contact names and numbers, evidence refs, appeal notes, cell and device codes) and scans every output file for each one.
- **What the export shows about staff:** only the *role* that recorded and confirmed each infraction, and per-role totals, never individuals. Limitation: in a very small facility, role plus week plus code might still point to a person; the small-cell rule helps for aggregates but not for individual records. Counsel should decide whether records need further coarsening or a delay.
- **Out-of-cell log** is append-only (trigger plus revoked grants, like the audit log and trust ledger): a correction is a new row and the latest entry for a day wins. Entry is audit-logged. A day with no entry is "not recorded", which is different from "zero minutes" and is flagged separately.
- **Welfare flags are computed on demand, not stored.** Each resident is compared with their own recent history (config `welfare`): no contact for N days (never-contacted residents are measured from when they got a device); usage or contact falling below 30% of their own 3-week norm over the last week (only if they were active enough for the norm to mean anything, and only with 4 weeks of history); out-of-cell time under the configured minimum; out-of-cell time unrecorded for several days (only counting days they have been on the unit). Staff can record a check-in, which is audit-logged and quiets that flag for a few days. "Usage" counts calls (including attorney calls, as a fact that a call happened), texts sent, orders, quizzes, staff requests, reading and chess moves. Job participation is deliberately not counted.
- **Activity timeline** (supervisor, admin, auditor): metadata only. Calls show contact type and length (attorney calls show only that one happened and how long), texts show direction and contact type but never the text, and no names or numbers appear. A written reason is required and every view is a `monitoring_access` audit entry. Job participation is left out so voluntary work never becomes part of a behaviour record.
- **Facility events** come in through the `FacilityEventSource` interface (mock) and `POST /mock/facility-events` (admin). A cell-camera obstruction makes a *pending* CAM_BLOCK with the event as system evidence; it never locks anything until a supervisor confirms. Events are idempotent by `event_id`. Out-of-cell minutes can be ingested the same way.
- **Texting (stub).** Tier-gated, monitored, daily limit from the tier, 500 characters. Attorney messages follow the same guard as attorney calls (invariant 6): the provider is told not to keep a copy, the guard checks it did not, no body is stored (DB CHECK), no reply row, and the thread shows "Sent privately". Monitored messages are stored and shown with a mock reply.
- **Video (stub).** Reuses the call plumbing with `medium = 'video'` and its own weekly minutes (separate from phone minutes). Attorney contacts are not offered video (they stay on the phone, where the privilege guard is). The device reports a covered camera; that ends the call and raises DEVICE_TAMPER from the system for a supervisor to confirm (once per call). There is no real camera or video in v1.
- **Chess (stub).** Engine from tier 2, human from tier 5, behind a `ChessProvider` interface that has only `new_game` and `submit_move`. There is no chat anywhere: no column, no method, no route (tested). The mock engine replays a fixed script and moves are format-checked only (no chess rules). Entitlements are re-checked on every move.
- **Reading (stub).** Four bundled public-domain or original texts in versioned config; general from tier 1, expanded from tier 4. Nothing is fetched from outside. `approved_content_sources` is the allow-list: if no bundled source is approved, nothing is readable; external sources must be https and are not used yet (the kiosk CSP would be extended from this table when they are).
- **Jobs (stub, section 8.1).** `job_listings` limited by a DB CHECK to non-personal task types; opt-in and leave are rows in `job_enrollments` with no audit entry, points, sanction, tier or entitlement change. The pay split lives in config and must total 100. Proof: tests count points, sanctions, tier and audit rows before and after joining and leaving, compare entitlements with and without a job, and scan the engine and points/sanction services for any mention of jobs (the jobs validator was moved out of `engine/` for this reason). Staff see only participant *counts*, never who.
- **Rec time (stub).** Slots and capacity are config. Indoor slots are part of the protected baseline; outdoor needs the `outdoor_rec` feature (tier 9+). Booking is today to a week ahead.
- **Bug fixes found by tests:** the weekly officer cap counted sanctions dated after the one being issued (only matters when a time is injected; now bounded); and a resident assigned today was flagged for "nothing recorded for a week".
- **Not done / deferred to Phase 8:** clean-day points and the daily tier check (needs the scheduled job in `simulate-week`), rate limiting, retention rules, and a UI for video and chess (placeholders only).
