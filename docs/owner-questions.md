# Owner questions (Phase 17, step 1)

Collected from `docs/DECISIONS.md`, `docs/STATUS.md`, `docs/ASSUMPTIONS.md` and a read of the Phase 17 to 23 brief. Each has a recommended answer. **Nothing below has been changed yet.** Work on Phases 17 to 23 waits for these answers.

## A. Open items already in the docs

1. **Invariant 17 and the welfare check** (`STATUS.md`, row 17, "Holds, one question"). The welfare flag compares a resident's activity with their own recent baseline and shows staff a flag. The text of the original question is not in the repo. My reading: is this an "individual risk score"? It feeds no tier, sanction or restriction, and nothing stores a score. *Recommend:* keep it, and record in DECISIONS that a welfare flag is a safeguard for staff review, not analytics. Add a test that no welfare output is read by the tier, sanction or restriction code, as invariant 12 already does for message flags.
2. **No-contact orders versus attorney contacts** (DECISIONS, Phase 11). The spec says no-contact orders "override everything". The build never blocks an attorney contact, because attorney access is protected baseline (invariants 1 and CLAUDE.md 4.1). *Recommend:* keep as built.
3. **Attorney video** (DECISIONS, Phase 11). It is allowed, unmetered, private, never recorded, but it is not baseline, so a video lock (for example after a confirmed DEVICE_TAMPER) also blocks it; the phone stays open. *Recommend:* keep as built. Invariant 1 names attorney calls only. Counsel to confirm.
4. **Quiz attempt limits versus baseline education** (DECISIONS, Phase 14). Basic education is baseline; the quiz has 5 attempts per 24 hours and a 10 minute cooldown. Lessons never lock. *Recommend:* for basic courses keep the cooldown but remove the daily attempt cap (config change only), so "no limits on baseline education" cannot be argued. Keep both for advanced courses.
5. **Reentry is not in `get_entitlements`** (DECISIONS, Phase 15). It is read-only information, never lockable, so it bypasses the entitlement function (invariant 2, read literally). *Recommend:* make it a named baseline feature so invariant 2 has no exception. It is a small change plus a test.

## B. Questions the new brief raises

6. **Chess engine licence (Phase 19).** The brief says to stop if only GPL engines are good enough. I have not checked licences yet. Strong engines are usually GPL (for example Stockfish, GPLv3), which brings source-offer duties and a legal question about bundling into a kiosk build. *Recommend:* do not bundle a GPL engine. Use `chess.js` (BSD-2, rules and move generation) with a small alpha-beta engine written for this project (MIT, in a Web Worker, no WASM), with difficulty set by search depth and a mistake rate. It plays well enough for residents, works offline, and has no licence risk. I will verify the `chess.js` licence before using it. Say if you would rather have a stronger GPL engine and accept the obligations.
7. **Order of Phases 19 and 20.** Chess matchmaking must never pair residents on the same line, but lines only exist after Phase 20. *Recommend:* keep the numbering, add a nullable `line_code` to cells in Phase 19 (filled at intake today, derived from the facility model in Phase 20).
8. **Line scheduling versus the out-of-cell minimum (Phase 20).** The brief says nobody from the same line is out at the same time unless staff allow it. A line has up to 4 floors of 16 cells, 64 residents. One person out at a time cannot give 64 residents the 60 minute daily minimum (it needs 64 hours). Invariant 1 says the minimum out-of-cell time never locks. *Recommend:* apply the one-at-a-time rule to outdoor rec slots only (it is configurable as `max_concurrent_out_per_line`, default 1), never to the baseline out-of-cell minimum, and add a capacity report that shows when a line's schedule cannot reach the minimum for its residents. The software flags the shortfall; it does not enforce a schedule that would break the minimum. Please confirm that is what you meant.
9. **Staff MFA scope (Phase 18).** *Recommend:* TOTP required for supervisor, admin and auditor, and for officers too, with 10 single-use recovery codes. Password reset by an admin only, audited, forcing a new password and MFA re-check at next sign-in. No self-service reset by email (there is no mail system).
10. **Encryption at rest (Phase 18).** *Recommend:* application-level AES-256-GCM on message bodies, contact numbers and recording metadata, with a key id stored next to each value and a `rotate-keys` script that re-encrypts in batches. Keys come from an environment secret or mounted file, not the database. Cost: encrypted columns cannot be searched in SQL; contact numbers get a keyed hash for duplicate checks. A cloud KMS or HSM is the production upgrade and is documented, not built.
11. **Retention periods (Phase 18).** `compliance.yaml` has no values for messages or call metadata. *Recommend:* ship the job with defaults unset (keep everything) in the real config, and set clearly marked placeholder values in the demo and test config (messages 365 days, call metadata 730, recordings 90). Counsel sets the real numbers. Audit and ledger tables are never touched, and a test proves it.
12. **Spanish legal and religious texts (Phase 18).** *Recommend:* use public-domain Spanish sources where I can verify them (for example Reina-Valera 1909 for the Psalm) and write unofficial translations of the Bill of Rights excerpts, each labelled "unofficial translation, counsel to verify" in the app and in ASSUMPTIONS.md.
13. **The failing `phase11` video test.** The test caps every request body at 100 characters, and the kiosk's health heartbeat (about 170 characters of storage and device status, no picture or resident data) trips it. It fails on the code from before the UI work too. It guards invariant 14. *Recommend:* have the test skip the `/device/heartbeat` route and keep the `data:`-URI and size checks on every other request. I will not touch an invariant test without your yes.
